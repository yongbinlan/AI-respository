# 验收与自审

先把用户目标转为能观察的失败条件，再选择最小充分检查。语法、路径、哈希和成功退出只能证明各自检查项。

| 交付对象 | 有用的结果检查 |
| --- | --- |
| 程序、Skill、自动化 | 代表性输入的完整路径、关键异常处理、输入输出契约；Skill 还需检查触发范围、引用、权限和适用的真实行为样本 |
| 页面、交互与动画 | 在目标运行环境打开，操作关键控件，检查代表性视口、布局、溢出和适用的动画行为 |
| 图片、视频、音频 | 实际查看或听取，检查构图、内容一致性、声音、同步及旧素材混入；按领域规范检查可用性 |
| 文档、表格、演示 | 检查事实与计算，预览最终排版、页数、空白、乱码、图表和可读性 |
| 研究、方案、文案、小说 | 核实来源与时效、假设与事实边界，实际阅读逻辑、节奏、承诺兑现和一致性；保留项目专用门禁 |
| 配置、工作流与规则 | 验证修改后的有效配置、引用链、优先级、冲突和可恢复的旧版本 |

## 自审的方法

暂时离开“我想怎么做”，从“用户拿到后如何使用”逐项检查：目标是否兑现、必需内容是否完整、是否偏离保留约束、关键路径是否顺畅、有什么已知限制会影响使用。重点审查实际成品与证据，避免凭创作意图打分。

检查发现缺陷后先修复，保存需要保留的旧版本，再复验受影响部分。必需方法不可用时说明失败、采用的替代方法、不能证明的部分以及完成验证所需条件；不能悄悄将更弱检查称为等价。

## 证据与结论

区分机械校验、实际执行、模型情景试用、独立评审、用户审阅和真实市场反馈。模型试用标记 `SIMULATED`，不是用户认可或效果实测；自审不能称为独立评审。安全、隐私、正式发布、核心正史或既有流程要求独立评审时，按适用规则执行。

交付说明遵循环境中适用的全局契约；没有现成契约时，用简洁文字或已有收据承载以下字段：目标、环境、验收、产物、实际检查、证据、未解决项、限制和状态。状态来自检查结果。`pending_user_review` 不豁免本可发现的缺陷；缺少必需证据时用 `verification_incomplete` 或 `blocked`。

安装 Skill 不证明已在每次对话中被自动选中，也不证明提高了真实任务成功率。需要时用新任务核验宿主发现情况，并通过实际使用迭代；不要只因文件存在就声称全局执行效果已保证。
